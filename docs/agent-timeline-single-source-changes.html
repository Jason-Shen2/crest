Architecture Refactor · June 2026

Agent Timeline 单一真相源

run 的身份从「凭空 mint 的 id + 位置匹配」改为「session user message 的 entry id」， JSONL session 成为唯一真相源，cmdblock 退化为有序投影。 历史上所有 session 相关 bug（刷页后卡住 loading、/tree 错位、/compact 后丢失 run 身份、/resume 错乱） 共享同一个根因，这次重构从根上解决。

f345bb68feat(harness): expose user entry id from prompt

8201857ffeat(renderer): key agent blocks on userEntryId
e4b98373fix(agent): drain pending send() resolvers on abort/dispose to avoid hang
(本轮)refactor: 全面删除 agent_run_id / runId，userEntryId 为唯一身份

为什么改

旧架构中，renderer 或 main 会凭空 uuidv7() 出一个 runId，把它写进 cmdblock 的 agent_run_id 列，再靠「位置顺序」把 session 分支上的 user messages 与 cmdblock 的 runId 对齐。 位置匹配在 session 过滤、顺序方向、compact 重建、异步到达等场景下都会错位， 这是刷页后 block 卡在「…loading agent run…」的根源。

核心洞察：run 的身份本就应该是启动它的那一条 user message 的 id。 既然每条 user message 在 session 里都有一个稳定的 entry id，那 runId 就不该是额外 mint 的东西—— 直接用 userEntryId 当 runId，重建时按 entry id 精确 join，与顺序、过滤、方向都无关。

5PaneSession 层 · run 构建与身份

emain/agent/pane-agent-session.ts

这是改动最集中的文件。分四块说：

5.1 新增 entryId-join 构建器

新增 buildRunsFromEntryIdJoin(entries, anchoredEntryIds: Set<string>)： 按 session 分支顺序遍历，遇到在 anchoredEntryIds 中的 user message 就开一个 run， 之后的 assistant/tool 消息归入当前 run，遇到下一个锚定 user message 就切下一个 run。 100% 确定性，与顺序、过滤、位置无关。

新增 buildPersistedRunsFromSessionEntries(entries, timelineRefs, path) 作为总入口： 从 refs 里收集所有非空的 agentuserentryid 成 Set（并按 agentsessionpath 过滤）， 始终走 entryId-join。开发阶段不兼容旧数据，旧的位置匹配逻辑 （buildRunsLegacyPositional 等 4 个函数）已整体删除。

5.2 send() 从 fire-and-forget 变为 Promise<string>

修改 旧签名 send(runId, text): void → 新签名 send(text): Promise<string>。 返回值是该次 send 对应 user message 的 userEntryId（= runId）。

机制：

  • 调用 send 时同步 push 一个 {resolve, reject} 到 pendingEntryIdResolvers FIFO 队列；
  • user message_end 到达（带 entryId）时， 用该 entryId 开 run，并 shift() 队头 resolver 来 resolve(entryId)；
  • prompt 或 followUp 失败时 shift() 队头 reject(err)，防止挂起；
  • abort / dispose 时整队列 reject（review 后补的修复，见底部）。

5.3 knownRunIds 伪 refs 彻底删除

删除

  • 类字段 private knownRunIds: string[] = []
  • 构造函数里 this.knownRunIds = initialRuns.map((r) => r.runId)
  • ensureRun 里维护 knownRunIds 的分支
  • rebuildFromCurrentBranch 里用 knownRunIds 构造伪 refs + 过滤回填的一大块

5.4 compact / rebuild 签名统一

Before
async compact(customInstructions?): void {
  await this.pane.harness.compact(customInstructions);
  await this.rebuildFromCurrentBranch(); // 靠 knownRunIds
  this.emitSnapshot();
}

private async rebuildFromCurrentBranch(
  timelineRefs?: AgentTimelineRef[]
): Promise<void> {
  // 没有 refs 就用 knownRunIds 造伪 refs
}
After
async compact(
  timelineRefs: AgentTimelineRef[] = [],
  customInstructions?: string
): Promise<void> {
  await this.pane.harness.compact(customInstructions);
  await this.rebuildFromCurrentBranch(timelineRefs);
  this.emitSnapshot();
}

private async rebuildFromCurrentBranch(
  timelineRefs: AgentTimelineRef[] = []
): Promise<void> {
  // 直接用传入的 refs；不再有伪 refs
  this.runs = buildPersistedRunsFromSessionEntries(
    entries, timelineRefs, this.path
  );
}

navigateTree 签名不变，仍是 navigateTree(targetId, timelineRefs?)。 因为 rebuildFromCurrentBranch 已改为默认 []，传 undefined 也没问题。

迁移与不兼容说明

仍在开发阶段，不保留向后兼容，agent_run_id / runId 已全栈删除：

  • DB：迁移 000016 drop 掉 agent_run_id 列与 idx_cmdblock_agent_run 索引；唯一身份列为 agent_user_entry_id。
  • 幂等键：block_id + agent_user_entry_id。
  • 重建：始终走 entryId-join；位置匹配 legacy 路径（4 个函数）整体删除。
  • Renderer：只读 row.agentuserentryid，无 agentrunid 回退。
  • 旧数据：未迁移的旧行（仅有 agent_run_id）将随列一起丢弃——开发阶段可接受。

Review 发现 & 修复

BLOCKER · 已修复（e4b98373）

Task 7 引入的 pendingEntryIdResolvers FIFO 队列， 在 abort 和 dispose 路径上没有 drain。 当一个 followUp 还在 harness 队列里未被 drain 就被 abort 清掉时， 它对应的 resolver 永远不会 resolve → send() promise 永久挂起， 且队头残留的 stale resolver 会让后续 send 错配。

修复：新增 rejectPendingSends(err) 辅助方法， 在 abort 事件处理和 dispose() 中调用，整队列 reject 并清空。 加 2 条回归测试覆盖。

NIT · 非阻塞，后续处理

  • 已处理 buildPersistedRunsFromTimeline 及其它 3 个 legacy 位置匹配函数已连同测试删除。
  • onSendError 的 shift() 在 burst 场景可能 reject 错的 resolver（语义不精，但不影响主路径）。
  • Go 层 AppendAgentRun 现已校验 UserEntryID 非空（在 wshserver handler 层）。
  • 几处陈旧注释还在用「mint synthetic runId」的旧措辞，可更新。
  • steer / nextTurn 的 user 消息会错误消费 resolver（当前 renderer 未调用，未来接入需处理）。
