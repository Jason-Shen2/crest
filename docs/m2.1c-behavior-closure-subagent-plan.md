- [ ] **Step 1: Add failing initial-registration and replacement tests**

Add named tests:

```text
publishes an initial root only after its complete widget-component revision validates
disposes every unique Bridge-owned factory component when initial candidate validation fails
does not dispose caller-owned external components when initial candidate validation fails
atomically replaces a persistent root only after the replacement revision validates
disposes rejected Bridge-owned factory replacement components while retaining the previous root
retains the previous root and caller-owned external replacement components when validation fails
disposes removed published components after replacement regardless of candidate origin
disposes all published unique components once on unregister regardless of candidate origin
rejects a second root that shares a published component and disposes the first root once
deduplicates repeated component identity within one rejected root
```

Ownership is explicit at the root-candidate boundary:

```ts
type WidgetComponentOwnership = "bridge-factory" | "caller-external";
```

- `bridge-factory`: the bridge/context created the root by invoking a function-valued widget/header/footer factory; the bridge owns every unique component reachable through adapter children, including a partially walked candidate;
- `caller-external`: the caller supplied an already-created component; candidate rejection must never transfer ownership to the bridge or dispose any reachable component;
- this ownership value exists only while an unpublished candidate is being validated or rejected;
- once a candidate publishes successfully, discard the ownership distinction: the Bridge owns lifecycle cleanup for every unique component in the published revision;
- published replacement removal, dynamic child removal, unregister, and bridge disposal always dispose removed/published unique components exactly once, regardless of candidate origin;
- deduplicate every rejected or published cleanup by component identity, so the same component referenced more than once is disposed at most once per lifecycle removal.

Initial registration cases:

- valid Box/Input root: all ids become routable in one synchronous publication;
- duplicate widget id, child mismatch, and cross-root id collision each return failure with no routable id and no `update`/host callback;
- for each rejection shape, a `bridge-factory` candidate disposes all unique components discovered or supplied for that candidate exactly once, including the root and children visited before failure;
- for each rejection shape, a `caller-external` candidate disposes zero candidate components;
- rejection never disposes components belonging to an already published root, even when the failed candidate collides with that root's id.

Replacement cases must exercise `setWidget(key, component)`, `setHeader(component)`, and `setFooter(component)`:

- build and validate the replacement while the old root remains published;
- on success, atomically swap target and component-to-root maps, then publish the new host value and dispose only removed old components;
- on failure, keep the old host value, old targets, and old registration fully live and leak no replacement targets;
- rejected `bridge-factory` replacement candidates dispose every unique candidate component exactly once;
- rejected `caller-external` replacement candidates dispose zero candidate components;
- replacement failure never disposes old-root components, regardless of old-root or candidate ownership;
- after either origin publishes successfully, a later successful replacement disposes every removed old published component exactly once;
- an old unregister handle invoked after successful replacement is inert and cannot remove the replacement.

Published lifecycle cases:

- publish one `bridge-factory` root and one `caller-external` root, then unregister each; both roots and all published children are disposed exactly once;
- successfully replace a published caller-external root; every removed old component is disposed exactly once and retained/shared components are not disposed;
- publish one root, attempt to publish a second root that shares one component identity even when its supplied widget id differs, and assert the second root is rejected without replacing the first root's target; disposing the bridge then disposes the first root's component exactly once;
- build one rejected root that references the same component identity more than once and assert rejection cleanup disposes that identity exactly once for `bridge-factory` and zero times for `caller-external`;
- invoke stale unregister handles and repeated bridge disposal after cleanup; disposal counts remain unchanged.
