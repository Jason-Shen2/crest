# M2.1C Pi GUI Behavior Closure Specification

## Status

Approved design. This document defines the implementation and acceptance boundary for M2.1C. It builds on the completed M2.1A adapter contract and M2.1B extension UI lifecycle contract.

## Goal

Close the behavior gap between standard vendored `pi-tui` components and their native Crest GUI controls without replacing Pi semantics with a second frontend-only state machine.

M2.1C is complete when:

- every M2 behavior requirement for standard components is `covered`;
- every standard component in `PiTuiComponentCompatibilityMatrix` has `certification: "passing"`;
- browser-native editing, selection, IME, clipboard, and accessibility remain intact;
- Pi component instances remain authoritative for extension-visible state, callbacks, filtering, selection, activation, cancellation, and loader lifecycle;
- all five standard certification fixtures have zero failures;
- `select-input`, `markdown-layout`, and `official-interactive` pass;
- `official-custom-unsupported` and `pi-gui-showcase` terminate as expected `unsupported` results solely because they contain a `terminal` fallback node;
- no fixture is promoted by hiding a matrix blocker or by treating unknown custom components as standard GUI components.

## Design Decision: Hybrid Authoritative

Neither a Pi-only event emulator nor a DOM-only rewrite is authoritative for all behavior. M2.1C uses an explicit hybrid authority model.

### Browser Authority

The browser owns behavior that only the native editable surface can implement correctly:

- DOM focus and blur;
- caret and selection ranges;
- `beforeinput`, `input`, composition start/update/end, and IME candidate placement;
- copy, cut, paste, and platform editing shortcuts;
- pointer selection and browser accessibility semantics;
- native scrolling needed to keep the caret or active option visible.

Crest must not translate ordinary printable input, composition updates, selection movement, or clipboard operations into terminal escape sequences. Doing so would discard browser semantics and duplicate the editor implementation.

### Pi Authority

The live vendored Pi component owns extension-observable semantics:

- canonical value and cursor snapshot after committed edits;
- filtered item set and selected index;
- wraparound keyboard navigation;
- `onSelectionChange`, `onSelect`, `onChange`, `onSubmit`, `onEscape`, `onCancel`, and settings callbacks;
- SettingsList value cycling and submenu activation;
- scoped Editor submit behavior, including trim, reset, `onChange("")`, and `onSubmit(result)`;
- loader frame progression, abort state, and disposal;
- the semantic widget snapshot emitted after a handled event.

The adapter must invoke public Pi methods or explicit public behavior methods. It must not reproduce Pi callback order or state transitions in React.

### Compatibility Matrix Authority

`PiTuiComponentCompatibilityMatrix` is authoritative for whether Crest may claim compatibility.

- A fixture cannot pass if it contains a standard component whose certification is `planned` or `unsupported`.
- A standard component becomes `passing` only when all of its behavior requirements are `covered` by focused evidence.
- A `partial` or `planned` requirement remains a certification blocker even if one fixture happens to exercise a happy path successfully.
- A `terminal` node always maps to `custom-component` and remains `unsupported` until M3 terminal-surface certification.
- Rich Crest components are governed by their separate rich-component contract and do not excuse or block standard Pi behavior unless their own certification explicitly says so.

### Rejected Alternatives

- **DOM-only authority:** rejected because direct callback invocation and React-local state can diverge from Pi filtering, activation, submit, and cancellation semantics.
- **Pi-only key emulation:** rejected because terminal key data cannot faithfully represent browser selection, composition, clipboard, pointer, or accessibility behavior.
- **Fixture-only certification:** rejected because a fixture can miss behavior requirements and accidentally overstate component parity.

## Scope

### In Scope

- Behavior closure for `Box`, `SelectList`, `SettingsList`, `Input`, `Markdown`, `Editor`, `Loader`, and `CancellableLoader`.
- Compatibility-matrix evidence updates for every requirement closed by M2.1C.
- Native GUI focus, keyboard, pointer, editing, IME, clipboard, scrolling, and accessible roles for standard components.
- Public Pi behavior methods needed to apply browser results without accessing private fields.
- Widget protocol fields needed to preserve focus, selection, filtering, visible ranges, submenu state, and loader lifecycle.
- Standard Editor value editing, cursor/selection preservation, composition, clipboard, newline handling, and submit/reset behavior.
- Certification-harness changes required to classify matrix-complete fixtures as passing.
- Exact certification outcome of three passing fixtures and two terminal-only unsupported fixtures.
- Focused component, adapter, bridge, DOM, timer, certification, and regression tests.

### Existing Contracts Preserved

- M2.1A stable component markers, public snapshots, concrete adapters, adapter-owned child discovery, WeakMap widget identity, and rich-component `Symbol.for` contract.
- M2.1B owner snapshots, replacement replay, reload handoff, request termination, canonical session identity, and bridge disposal.
- Unknown custom components render as `terminal` and receive only the existing debug fallback key/cancel behavior.
- JSON field names remain lowercase without underscores.

## Non-Goals

- M3 terminal-surface support for unknown custom components.
- ANSI parsing, terminal cursor emulation, terminal resize, OSC links, or terminal IME.
- Pixel-identical reproduction of Pi terminal glyphs, colors, borders, or line wrapping.
- Replacing browser text controls with a custom canvas/contenteditable editor.
- Adding an Editor cancel callback that Pi does not expose.
- Treating the existing unsupported Editor cancel intent as successful behavior.
- Editor autocomplete, suggestion lifecycle, prompt history navigation, and history draft restoration.
- Editor large-paste compaction, paste-marker storage/expansion, and large-paste undo semantics.
- Adding autocomplete, history, or large-paste requirements to `PiTuiComponentCompatibilityMatrix`; these behaviors are outside M2.1C certification.
- RichTable keyboard navigation, sorting, virtualization, or other rich-component maturity work.
- Extension lifecycle, replay, reload, persistence, or runtime ownership changes already covered by M2.1B.
- New extension APIs, IPC channels unrelated to widget behavior, package dependencies, or generated files.
- Product UX redesign of the extension panel.

## Common Event Contract

### Event Phases

Every standard widget interaction follows one of two paths.

**Native edit path:**

1. The browser applies the edit, composition, selection, or clipboard operation to the DOM control.
2. React records local transient DOM state without remounting the control.
3. On a committed value change, Crest sends one semantic `change` event containing the complete current value and any required selection metadata.
4. The adapter applies the complete value through a public Pi method.
5. Pi callbacks run according to the vendored component contract.
6. The bridge snapshots the live component and emits the authoritative widget update.
7. React reconciles the snapshot without replacing an actively composing control or losing its selection.

**Pi action path:**

1. React sends a semantic action or a Pi key action.
2. The adapter validates the payload and invokes one public Pi behavior.
3. Pi mutates state and invokes callbacks.
4. The bridge snapshots only after the action completes.
5. The renderer updates active state, visible range, labels, or completion state from that snapshot.

### Linearization And Races

- Adapter mutation is the linearization point for a committed semantic event.
- The bridge must rerender only after `{ handled: true }`.
- Event ordering for one widget is FIFO.
- A snapshot echo of the value already held by an active DOM editor must not remount the editor or reset selection.
- During composition, stale owner snapshots must not overwrite the composition buffer.
- Composition commit sends one final value change; intermediate composition text must not trigger Pi submit or cancel.
- Submit flushes the latest committed DOM value to Pi before invoking Pi submit semantics.
- A stale event after M2.1B target disposal is ignored.
- Invalid payloads are unhandled, do not mutate Pi state, and do not trigger a rerender.

### Event Acknowledgement Scope

- Renderer-originated semantic events may carry lowercase `eventid`, an opaque, non-empty string of at most 256 UTF-16 code units. IDs are strictly unique within one renderer process and collision-resistant across processes.
- The renderer uses `crypto.randomUUID()` when available. Its tested fallback combines one renderer-module random prefix with one module-global monotonic counter; IDs are compared only for exact equality and are never parsed or ordered.
- Each mounted node tracks its own exact pending IDs. Replacing the node id remounts that renderer and clears its pending set.
- A successful handled refresh copies `eventid` to lowercase `ackid` only on the serialized node whose id equals the event target. The root, siblings, newly added nodes, and unrelated nested nodes carry no acknowledgement.
- Initial and scheduled publications carry no `ackid`. Invalid, unhandled, stale-target, snapshot-failure, validation-failure, and publication-failure paths emit no acknowledgement.
- `WidgetEventDispatchResult` is `{ handled: boolean; published: boolean }` and is preserved across Bridge, runtime, IPC/preload, renderer globals, `use-pi-chat`, and the AgentExtUi callback promise.
- `{false,false}` means invalid, stale, or adapter-unhandled. `{true,false}` means Pi mutation succeeded but refresh/publication failed. `{true,true}` means the acknowledged live revision was published.
- A rejected delivery promise is an unconfirmed causal nack. A legacy void callback is also immediately unconfirmed, even though synchronous collectors still receive the event. Both remove only that pending ID and never guess an immediate rollback.
- Input stores pending value events as an insertion-ordered `Map<eventid, tuple>`. Removing an older nack leaves the newest tuple authoritative for deduplication; removing the newest recomputes `lastSent` from the newest remaining tuple or the last authoritative/accepted tuple so the same DOM tuple can retry.
- `{true,false}` removes the corresponding pending ID and marks its local tuple accepted. It still carries no `ackid`, and the next no-ack authoritative snapshot may reconcile value and selection.
- A dirty node accepts an `ackid` only when it exactly matches one of that renderer instance's pending IDs. Foreign, late, or replayed acknowledgement metadata is treated as no-ack while dirty; while clean, that metadata is ignored and the authoritative value and selection still reconcile.
- For multiple pending value events, an older exact acknowledgement may settle only itself and must not roll back the latest dirty DOM state. An acknowledgement for the latest value event settles all superseded value-event IDs; later old acknowledgements are replay and remain inert.
- While a value event remains pending, no-ack snapshots cannot overwrite the dirty DOM state. Once the latest exact acknowledgement settles it, a later no-ack authoritative snapshot may reconcile value and selection.
- `ackid` is live-delivery metadata only. The live extension UI delta keeps it, but `AgentSessionRuntime` recursively strips it before storing `extensionUi`, producing a late-subscriber replay, or creating reload handoff state.
- Input selection-only movement emits one complete `change` with the unchanged value, current selection tuple, and a fresh `eventid`. The renderer deduplicates the complete `(value, selectionstart, selectionend)` tuple so a following native input/change observation of the same tuple emits nothing.

### Root Invalidation Contract

Every registered widget tree has one live root component and one root update callback.

- A handled adapter event calls `rootComponent.invalidate()` exactly once, even when the event targets a nested child.
- Invalidation happens after the Pi mutation and callbacks complete, and before the next root snapshot is created.
- The bridge snapshots the root, never only the event target, so parent layout, sibling status, submenu replacement, and callback-driven mutations appear in one update.
- Loader/TUI `requestRender()` coalesces pending work per root; it schedules the same root invalidation and snapshot path rather than serializing independently.
- Multiple invalidations before the scheduled snapshot may coalesce into one snapshot, but a handled synchronous event must not publish a pre-mutation tree.
- An unhandled event, stale target, or invalid payload does not invalidate or publish.
- Root disposal cancels queued invalidation work; no update callback runs after unregister, reload, or owner disposal.

### Dynamic Target Reconciliation

Targets are derived from every authoritative root snapshot, not only from the initial registration.

1. Invalidate the live root when required by the root invalidation contract.
2. Serialize the complete root into a candidate `WidgetNode`.
3. Walk the candidate widget tree and the live component tree through adapter-owned child discovery into a candidate target map.
4. Validate unique node ids and widget/component child pairing before publishing.
5. Atomically replace that root's published widget and target map.
6. Make newly introduced targets routable, make removed targets stale, then invoke the root update callback with the same published candidate widget.

Reconciliation rules:

- Event lookup observes either the complete previous map or the complete next map, never a partially rebuilt map.
- A snapshot and its target map are one revision; the renderer must never receive a widget whose ids still resolve through another revision's targets.
- Submenu open/close, filtered children, and any callback-driven subtree replacement are reflected by the next revision.
- Unchanged live component objects retain their adapter-owned widget ids; new objects receive new ids.
- Removed components are adapter-disposed exactly once when no target in the next revision references them.
- Components retained in the next revision are not disposed during map replacement.
- If serialization, validation, or target-map construction fails, the previous widget and target map remain published and no partial update is emitted.
- Per-root unregister atomically removes that root's current map before disposing its unique live components.

### Focus Contract

- The DOM reports focus changes; the adapter updates the public Pi focus state before snapshot.
- Focus is represented in the widget protocol for all focusable standard components.
- A focused widget remains keyboard routable after an authoritative snapshot refresh.
- Session replacement, request termination, or widget removal may release focus; ordinary snapshot refresh must not.
- Focus restoration must not steal focus from the composer or another explicitly focused control.

## Component Behavior Contracts

### Box And Markdown

`Box` passes when child order, nested target identity, `paddingx`, and `paddingy` are preserved in the DOM and nested events continue to reach the matching live child.

`Markdown` passes when the source is rendered through Crest's semantic Markdown renderer, padding is honored, and source content used by certification remains observable. Pi terminal theme functions and terminal-width wrapping are not visual parity requirements.

These contracts close `child-layout` and `source-rendering`; they do not require terminal pixel parity.

### SelectList

The live `SelectList` remains authoritative for filtering and selection.

Required behavior:

- Arrow Up and Arrow Down call Pi navigation and wrap at both ends.
- Enter activates the Pi-selected item and invokes `onSelect` once.
- Escape invokes `onCancel` once.
- Navigation invokes `onSelectionChange` with the newly selected item.
- Pointer selection first sets the Pi selected index, then activates that item.
- Filtering calls Pi `setFilter()` with the complete query, uses Pi's case-insensitive value-prefix rule, and resets selection to index `0`.
- Empty filtered results render a no-match state and cannot activate an item.
- At most `maxvisible` options are rendered in the active window.
- The active option remains visible as selection moves.
- `role="listbox"`, `role="option"`, `aria-selected`, and `aria-activedescendant` reflect the Pi snapshot.
- Focus state is observable and controls keyboard routing.

React must not maintain an independent selected index after Pi acknowledges an event.

### SettingsList

The live `SettingsList` remains authoritative for search, selection, value mutation, activation, submenu handoff, and cancellation.

Required behavior:

- Arrow Up and Arrow Down wrap over the current displayed item set.
- Search input uses Pi's fuzzy filtering, resets selection to index `0`, and exposes the current filter.
- Left and Right cycle values immediately in their respective direction and invoke `onChange(id, value)` once.
- Enter and Space invoke Pi activation.
- Activating a `values` item cycles to the next value using Pi order.
- Activating a submenu item opens the Pi-created submenu component.
- Submenu events route to the submenu while it is active.
- Submenu completion applies a defined value, invokes `onChange` once, closes the submenu, and restores the parent selection.
- Submenu cancellation closes the submenu without changing the value.
- Escape on the main list invokes the parent `onCancel` once and does not roll back prior immediate changes.
- At most `maxvisible` settings are rendered, with the active item kept visible.
- Labels, descriptions, current values, no-match state, selected state, and active submenu state come from the Pi snapshot.

The widget protocol and public snapshot must expose enough state to represent search and submenu behavior without serializing callbacks or component internals.

### Input

The browser owns the native single-line editing surface; the live Pi `Input` owns canonical value, callback, and submit/cancel semantics.

Required behavior:

- Typing, deletion, Home/End, word movement, selection replacement, copy, cut, paste, undo, Unicode graphemes, and IME composition use native browser behavior.
- A committed DOM change updates Pi through a public complete-value operation.
- The complete-value operation preserves a valid Pi cursor and accepts explicit caret metadata when required by the contract.
- Newlines are not retained in the single-line value; pasted tabs follow the Pi normalization contract where applicable.
- Enter flushes the current value and invokes `onSubmit` once with that value.
- Escape invokes `onEscape` once and does not submit.
- Submit and cancel buttons are behavior-equivalent alternatives to the keyboard actions.
- Focus and current cursor position are reflected in snapshots without disrupting browser selection.
- A remote authoritative value change updates the DOM when the control is not composing.

Pi kill-ring and terminal escape-sequence implementation details do not need to run for browser-native editing. The observable result and callback order must be equivalent.

### Editor

The browser owns the native multiline editing surface; the live Pi `Editor` owns canonical text, change callbacks, and submit semantics within the M2.1C scope.

Required behavior:

- Native multiline selection, caret movement, composition, copy, cut, paste, and undo remain available.
- Committed edits update Pi through a public complete-text operation and invoke Pi `onChange` semantics.
- Newlines normalize to `\n`; tabs normalize according to the Pi editor contract.
- Enter behavior distinguishes submit from newline according to the configured Pi keybinding contract.
- Submit trims the returned value, resets the standard editor buffer, invokes `onChange("")`, then invokes `onSubmit(result)`.
- Cursor and selection survive ordinary authoritative snapshot refresh.
- Long content keeps the caret visible and exposes scrolling without requiring Pi's terminal-height formula to be pixel-identical.

Autocomplete, prompt history, and large-paste marker behavior are explicitly outside this contract and contribute no requirement or evidence to the M2.1C matrix.

The vendored Pi `Editor` has no supported cancel callback. Therefore:

- the standard Editor renderer does not emit a `WidgetEvent` with `type: "cancel"`;
- the standard Editor adapter does not accept or fall back from `cancel`;
- the standard Editor control exposes no component-level cancel button;
- `cancel` is `not-applicable` for the standard Editor component unless the upstream public contract adds a callback;
- dismissal of an outer `ctx.ui.editor()` request is handled by the request container, which resolves the request with `undefined` without dispatching any widget event to the Editor;
- request dismissal remains a separate M2.1B behavior and is not evidence for Pi `Editor` component cancellation.

### Loader And CancellableLoader

Required behavior:

- A loader snapshot exposes the current frame and label.
- Default animation starts immediately and advances through the Pi frame sequence every 80ms.
- Custom `frames` preserve order and use a positive custom `intervalMs`; invalid or absent intervals use 80ms.
- Zero or one frame creates no repeating timer.
- Each frame advance requests a rerender and produces an updated semantic snapshot while the target is live.
- `stop()` is idempotent and prevents future frame updates.
- Bridge disposal stops Loader and disposes CancellableLoader exactly once.
- CancellableLoader cancel invokes `onAbort` at most once, exposes `aborted: true`, and stops animation.
- Plain Loader rejects cancel.
- No timer or rerender survives target disposal, owner reload, or owner disposal.

Timer-backed tests use fake timers and assert frame order, cadence, rerender count, cancellation, and disposal.

## Certification Fixture Contract

The default certification set remains exactly five fixtures.

| Fixture | Expected result | Required reason |
| --- | --- | --- |
| `select-input` | `passed` | Standard Box, SelectList, Input, and Text requirements are covered |
| `markdown-layout` | `passed` | Standard Box, Markdown, Spacer, Text, and TruncatedText requirements are covered |
| `official-interactive` | `passed` | Standard interactive components, Image, Loader, and CancellableLoader requirements are covered |
| `official-custom-unsupported` | `unsupported` | `terminal fallback widget requires M3 terminal surface certification` |
| `pi-gui-showcase` | `unsupported` | The fixture intentionally contains one unknown custom component serialized as `terminal` |

Expected aggregate:

```text
status: failed
gateStatus: passed
total: 5
passed: 3
unsupported: 2
failed: 0
```

The two status fields have different consumers and must not be collapsed:

```ts
interface PiOfficialExampleCertificationReport {
    status: "passed" | "failed";
    total: number;
    passed: number;
    unsupported: number;
    failed: number;
    // Existing generic report fields remain unchanged.
}

interface M21CBehaviorClosureGateResult {
    gateStatus: "passed" | "failed";
    report: PiOfficialExampleCertificationReport;
}
```

`status` remains the generic certification result. `gateStatus` belongs only to the M2.1C behavior-closure milestone gate and is not a third generic report status.

Classification rules:

- Missing component kinds, failed visible assertions, unhandled required events, callback-order violations, or unexpected errors produce `failed`.
- Matrix blockers on standard component kinds produce `unsupported` until closed; after M2.1C, no standard kind may produce such a blocker.
- A fixture containing `terminal` is `unsupported`, not `failed`, when all observable assertions pass and the only unsupported reason is the M3 terminal-surface reason.
- `pi-gui-showcase` must remain unsupported even though its standard and rich nodes work, because its explicit terminal fallback is observed.
- Removing the terminal node from either unsupported fixture to obtain a passing count is not allowed.
- Unsupported fixtures do not invalidate M2.1C when they match the exact terminal-only expectation and there are zero failed fixtures.
- Any additional unsupported reason, any third unsupported fixture, or any failed fixture fails the M2.1C gate.
- The generic report `status` type remains exactly `"passed" | "failed"`.
- The generic report has `status: "failed"` whenever `failed > 0` or `unsupported > 0`; therefore the accepted 3/2/0 aggregate still has generic `status: "failed"`.
- M2.1C adds a separate `gateStatus`, which is `passed` only for the exact accepted set: 3 passed, 2 unsupported, 0 failed, with `official-custom-unsupported` and `pi-gui-showcase` as the only unsupported fixtures and the M3 terminal-surface reason as their only unsupported reason.
- Every other count, fixture identity, unsupported reason, or any failed result produces `gateStatus: "failed"`.
- Only the M2.1C milestone gate consumes `gateStatus`; generic certification callers, compatibility reports, and future milestones continue consuming the generic report and its `status`.
- Computing `gateStatus` must not mutate, reinterpret, or overwrite the nested generic report.

The certification test must assert each fixture result, the exact aggregate, generic `status: "failed"`, and milestone-only M2.1C `gateStatus: "passed"`.

## Failure Semantics

- Invalid indices, ids, values, selection metadata, or event payloads are unhandled and non-mutating.
- Events for stale or disposed node ids are inert.
- A standard component with a broken public behavior contract fails focused tests; adapters must not fall back to private fields or React-local emulation.
- A DOM edit rejected by Pi restores the next authoritative snapshot without invoking submit or cancel.
- Composition cancellation does not commit partial text.
- Repeated submit, cancel, submenu completion, or loader abort settles the corresponding callback at most once per action.
- Root snapshot or target reconciliation failure retains the complete previous revision and emits no partial widget update.
- One component failure must not promote the fixture to unsupported; unexpected runtime behavior is `failed`.
- Unknown custom components remain terminal-only and must not be identified by constructor name or method shape.

## Test Strategy

### Pi Contract Tests

Focused vendored-component tests prove:

- SelectList wraparound, filtering, no-match, callback order, and visible-range calculation;
- SettingsList search, fuzzy results, immediate value changes, activation, submenu completion/cancel, parent selection restoration, and no rollback on cancel;
- Input complete-value/caret updates, submit, escape, and normalization boundaries;
- Editor complete-text updates, submit/reset callback order, and the absence of component-level cancel dispatch;
- Loader default/custom cadence, frame order, stop, abort, and disposal.

These tests are the semantic oracle for adapter and DOM tests.

### Adapter And Bridge Tests

Tests prove:

- each semantic event invokes the corresponding public Pi behavior once;
- handled events snapshot after mutation;
- invalid payloads do not rerender;
- focus and selection metadata round-trip without private access;
- every handled event invalidates the root exactly once before snapshot;
- each snapshot atomically reconciles the complete dynamic target map;
- submenu child targets become routable on open and stale on close without a partial target revision;
- failed reconciliation retains the previous widget/target revision;
- loader invalidation emits updated snapshots while live;
- stale targets and disposed timers are inert;
- M2.1A marker, snapshot, WeakMap identity, lookalike rejection, and terminal fallback invariants remain green.

### DOM Interaction Tests

Use React Testing Library and user-event where browser behavior is representable. Tests cover:

- Input typing, selection replacement, paste, Enter, Escape, focus, and snapshot echo without remount;
- explicit composition events proving no intermediate submit and one final committed change;
- Editor multiline editing, selection, ordinary native paste, composition, submit/newline distinction, focus, and scroll visibility; large-paste marker behavior is not asserted;
- standard Editor renders no component cancel control and emits no cancel widget event; outer request dismissal resolves only the request;
- SelectList keyboard wraparound, activation, cancel, filter, no-match, max-visible window, pointer selection, and ARIA state;
- SettingsList navigation, immediate left/right change, Enter/Space activation, search, submenu handoff, cancel, max-visible window, and ARIA state;
- Box padding/nesting and Markdown semantic rendering;
- loader frame and cancellation rendering.

JSDOM limitations must be isolated behind focused helpers. Clipboard tests prove only that synthetic DOM `cut`/`paste` events are not prevented and that the subsequent native-style `input` event emits a complete payload. They do not prove OS clipboard integration, permissions, or browser clipboard mutation. A test must not claim native IME or clipboard coverage by assigning `.value` directly.

### Certification Tests

`pi-official-examples.test.ts` asserts:

- the exact `3 passed / 2 unsupported / 0 failed` aggregate;
- generic report `status` remains `failed` because the aggregate contains unsupported fixtures;
- M2.1C `gateStatus` is `passed` for the exact accepted aggregate and fixture set;
- non-M2.1C consumers receive no alternative generic status and do not use `gateStatus`;
- no standard component contributes an unsupported reason;
- the two unsupported fixtures have only the terminal-surface reason;
- visible behavior assertions remain green;
- multi-instance targeting continues to use stable labels and does not hit the wrong live component;
- rich `Symbol.for` components remain semantic across jiti loader boundaries.

### Regression Tests

The expanded gate retains:

- M2.1A walker and adapter invariants;
- M2.1B owner snapshot, replay, reload, termination, and canonical identity tests;
- extension bridge and IPC routing tests;
- renderer reducer and extension UI tests;
- official examples and compatibility-report tests.
